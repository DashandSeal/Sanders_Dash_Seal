# Oracle production bootstrap and maintenance

The owner-requested bootstrap is deploy.sh at the repository root. The original
submitted script is preserved at owner-submitted/deploy.proposed.sh.txt. This
revision retains OL9, Docker Compose v2, firewalld, /opt/sanders-dash-seal, the
existing Node/Python stack, local persistent volumes and free certificate plan.
It has not been copied into the Oracle home directory or executed on that host.

## Before a real deployment

Use the complete approved Git checkout, not an empty mkdir-created project.
The script stages a clean committed checkout under /opt and freezes the exact
commit ID passed to the independent authorizer before archiving it. Private runtime
configuration belongs in root-owned /etc/sanders-dash-seal/runtime.env mode 0600;
its SANDERS_RUNTIME_FACTORY must name a real independently verified factory.
Trusted adapters can be installed root-owned under /etc/sanders-dash-seal/adapters
and are mounted read-only with SELinux labeling. Credentials do not enter Git.

/etc/sanders-dash-seal/authorize-release must be a real administrator-installed,
root-owned executable, not group/world writable. It receives checkout path and
commit ID and must verify independent source/dependency/runtime approvals. It is
not generated by this package. Existing unsigned PBD pairs, missing genuine
runtime bindings or unresolved release requirements are not automatically waived.
The script never invents a production authorizer returning success.

Inspect the active host firewall and preserve working SSH access first. If
firewalld is inactive, application stops before changing it; automatically
starting a firewall remotely can change access. HTTP/HTTPS are added to the zone
of the actual default-route interface, both runtime and permanent, without a
flush/reload or removing existing services. OCI NSG/security-list rules remain
separate. Docker also manages forwarding/NAT rules; this is not a replacement
for OCI ingress policy.

The engine installer uses Docker's actual RHEL repository definition, not the
https://docker.com website as a yum repo. That compatibility path still needs
validation on this Oracle Linux host. Existing engines are not uninstalled or
blanket-upgraded. DNF/package conflicts stop the script rather than removing
other software automatically. Compose daemon/plugin readiness is checked.

Confirm the instance still has public IP 129.146.111.166. In the existing DNS
zones, point each domain's apex A record to that IP and retain www as its root
CNAME (or equivalent A record). Preserve mail/MX/TXT/DMARC records. All four names
must reach this host for the bundled HTTP-01 issuance; correct stale AAAA records
as well. No GoDaddy record is changed by this script. The IP is ephemeral and
must be rechecked before a later cutover.

## Script behavior and commands

From the clean approved checkout:

```sh
bash deploy.sh --check
sudo bash deploy.sh --apply
```

If you separately copy deploy.sh into the Oracle home directory, retain the
complete approved checkout and pass SDS_SOURCE_DIR explicitly, for example:

```sh
sudo env SDS_SOURCE_DIR=/home/opc/Sanders_Dash_Seal bash /home/opc/deploy.sh --apply
```

Those are instance paths, not files installed by this session.

--check only validates source/configuration layout and a clean Git worktree; it
makes no host changes and does not grant release authority. --apply requires root,
OL9 on ARM64/x86_64, active firewalld, the real authorizer and protected runtime
configuration. Fixed systemd templates currently require the default /opt and
/var/lib paths and the sanders-dash-seal Compose project. Existing containers with
a different project/volume identity cause a stop for explicit migration review.

The script checks for unrecognized existing source files, stages approved source,
validates Compose, builds Node/Python images, obtains certificates if absent and
starts/reconciles the three application containers. It never runs compose down
or deletes volumes. It does not mount a new network Vault: the selected Docker
volumes are host-local certificate, challenge and SQLite storage. Their ownership
is managed by the actual container images; Node's UID 1000 is not assigned to
Python's UID 10001 data. Root keeps ownership of deployment source files.

## Initial certificate and renewal

The production override is deploy/compose.production.yml. It adds actual certbot
and acme-bootstrap services sharing the named challenge/certificate volumes with
Nginx, plus health checks and the protected backend runtime configuration.
Initial issuance starts the HTTP-only challenge service before any TLS Nginx
needs missing certificate files, requests one certificate for all four actual
names using the supplied email and agreement flags, then stops that staging
service and starts TLS Nginx. Issuance failures stop without a live claim.

The sanders-certbot-renew timer checks twice daily with randomized delay. Its
script renews through the webroot, tests Nginx configuration and gracefully
reloads only when the served fullchain changes. It does not restart the entire
stack or mount Docker's socket inside Certbot. No production ACME request or dry
run has been performed by this session; CI only runs certbot --version.

Graceful certificate reload avoids intentionally tearing down established proxy
streams. One VM and one replica per service do not guarantee zero downtime:
application recreation, host maintenance or failure can disconnect sockets.
Clients still need reconnect/retry behavior using stable transaction request IDs.

## Validation before reporting live

The script requires Python /readyz success from the container and valid external
TLS responses for the canonical domain and aliases. It tests real Nginx config
and uses the complete IP with Host/SNI names. Example host checks:

```sh
cd /opt/sanders-dash-seal
sudo docker compose -p sanders-dash-seal -f docker-compose.yml -f deploy/compose.production.yml ps
curl -I --resolve sandersdashandseal.com:80:129.146.111.166 http://sandersdashandseal.com/
curl --fail --resolve sandersdashandseal.com:443:129.146.111.166 https://sandersdashandseal.com/readyz
sudo docker compose -p sanders-dash-seal -f docker-compose.yml -f deploy/compose.production.yml logs --tail=50 pipeline-worker
```

HTTP returns 308 for the canonical Host; an unrecognized raw-IP Host is rejected
by the existing Nginx policy. A process being Up or logs lacking errors does not
prove authenticated WebSocket operation. Test a real authorized /ws client from
outside the instance separately; do not paste its credentials into chat/logs.
Backend health checks reflect readiness; worker /health reflects process liveness.

After successful validation, the script installs root-owned systemd units for
certificate renewal and 15-minute deployed-source integrity checks. Integrity
checks compare file hashes, permissions, owners, missing files and unexpected
additions to a baseline outside the source tree. They fail/log in the journal
and do not automatically repair or bless drift. This root-local baseline is not
a digital signature or protection against an attacker controlling root and the
baseline together. GitHub SMTP alerts cover GitHub audits; they are not silently
connected to runtime journal events.

No Oracle packages/firewall/files/timers, DNS, live certificates or credentials
have been changed by preparation/testing. No paid service was provisioned.
